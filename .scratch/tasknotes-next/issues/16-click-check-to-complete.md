# 16: Click a Task's check to complete it

**What to build:** The round check at the left of every Task row becomes a button: clicking it completes the Task, clicking it again reopens it.

**Blocked by:** 13 — Drag Tasks into a Custom Order (same row markup; build on it to avoid conflicting edits)

**Status:** ready-for-agent

**Implementation:** in progress — Draft PR

## Comments

**2026-11-10 — owner request and decisions (Han), Q45–Q47:** "Buat agar tombol lingkaran task itu bisa dipencet untuk menandai task sebagai selesai", including In Progress Tasks. The check toggles: complete ↔ reopen; on a Won't Do Task it clears Won't Do; completing shows an Undo bar and plays the completion sound.

**2026-11-11 — implementation notes (Draft PR), for the owner.**
- Open, needs Han: Undo after completing a **Ready** Task from the check brings it back **In Progress at 0%**, not Ready. The core's `change_task` refuses Ready for any Completed Task ("Ready is only available for work that has not started"), and changing that is a core rule shared by the CLI and MCP (ADR 0006), so it was not changed here. For an In Progress Task, Undo restores status and progress exactly. Options: keep it; or a core rule that a completion taken back at once (revision checked) returns the Task to Ready, which touches `crates/tasknotes-core/src/tasks.rs`.
- Open: after a check moves its Task to another group, keyboard focus falls to the window, as it does for the status capsule; following the Task would scroll the list, which PR #21 forbids. Pinned with the other "waiting for the owner" focus cases.
- Choices: Undo is offered only after the check completes a Task (not after the status capsule, reopening or clearing Won't Do); it is not on ⌘Z, which stays "Undo the latest move to Removed"; one bar shows at a time, the newer taking the place of the Removed notice; the bar says "Task completed" with an Undo button, the owner's wording without the dot.

**2026-11-11 — owner decision Q48 (Han):** reopening a Completed Task, through the check, Undo, the status control, the CLI or MCP, returns it to the work status it had before it was completed: completed from Ready → Ready at 0%; completed from In Progress → In Progress with its previous incomplete progress. One core rule (ADR 0001), recorded as an addendum to ADR 0006. This settles the open Undo point above; the criterion is ticked.
- How: the core reads `completed_from` from the Progress Entry that completed the Task (the latest whose previous status is not Completed), with no schema change, and treats the Task as the one it was, like Won't Do's `wont_do_from`. All completion paths write that entry (status control, progress 100%, a dated update, bulk status, the check): core `tests/reopen.rs`. A Task completed before Progress Entries existed keeps the earlier rule (counts as started). Exposed as `completedFrom` (desktop) and `completed_from` (CLI, MCP; contract tests in `crates/tasknotes-cli/tests/tasks.rs`, `crates/tasknotes-mcp/tests/crud.rs`). The check reopens to it, Undo restores the exact status and progress, and the status control offers Ready to such a Task.
- Choice, pending the owner's confirmation: choosing In Progress explicitly (status control, CLI, MCP) on a Task completed from Ready starts it at 0%, as for a Won't Do Task; reopening to Ready is choosing Ready, which the check and Undo do.

**2026-11-11 — review fixes (Draft PR #35).** One check at a time: the second click of a double click is ignored and the checks pause 400 ms after a click, so the row that slides under the pointer is not checked too; every check is disabled while any Task's save or a move is on its way (no silently dropped click, no race with `reorder_task`); focus follows the slot without scrolling and the live region says what happened; the arrow keys move between checks; the new Task toast and the Undo bar share one hold timer (`useHoldTimer`), so both leave at least 1 s after the pointer or focus lets go; `checkTask` reads the core's answer as a return value and the Undo hook watches the revision itself.

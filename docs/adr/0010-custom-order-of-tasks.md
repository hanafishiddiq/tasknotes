# Tasks keep a Custom Order per List

Status: accepted (2026-11-09, Ticket 13, owner decisions Q5/Q6/Q16/Q17/Q31; amended 2026-11-10 by Q35/Q36/Q37)

A person drags Tasks within a work-status group of one List (Inbox included) to give them a **Custom Order**. It reuses ADR 0007's sibling positions and its "after a named sibling, or first" write, so the desktop, the CLI and MCP share one rule.

**Storage (schema v20).** Each Task has an integer `position`, one sequence per List (or Inbox), whatever its status. Sorted by Custom, a List shows In Progress → Ready → Completed as always, each group in that sequence. So a status change never needs a write of its own: the Task shows in its new group at the place it already had in the List. Upgrading gives every List's Tasks starting positions, Newest first (where a new Task lands), and changes no revision. Nobody sees those positions: every view still opens by Highest priority, and a List shows Custom only once it is switched to it, which starts it from the order on screen (below). A new Task, or one moved in from another List, takes a position below every other in its List, so it lands at the top of its group.

**The write.** `reorder_task` places one Task directly after a Task, directly before one, or first, always among the shown Tasks of its own group. An anchor that is gone, in Removed, in another group or another List is `revision_conflict`; nothing then moves and no status changes. Only the moved Task's revision is checked and bumped, and only it leaves an Audit Entry (`task.reorder`). The Tasks it passes are renumbered without a revision or an Audit Entry of their own: only positions change, so a neighbour's open edit never conflicts with a move going past it. Renumbering starts at the lowest position the List already has, so a move rewrites only the Tasks it passes. It is one Task, so it never goes through Bulk Change approval.

**Switching to Custom.** A List switches to Custom in three ways, all in the core and all in one transaction with what they rewrite:
- *A drag* under another sort. The desktop says which sort it was showing; when that is Priority, Newest or Difficulty, the core first rewrites the List's whole Custom Order to that order (not only the loaded page), then moves the Task and remembers Custom for the List.
- *Choosing Custom* from the sort menu (Q35). A List without a Custom Order of its own starts one from the order on screen, the sort the view remembers, as a drag does. A List that has one, because it showed Custom before (`view_sorts.custom_kept`), gets that one back, so switching to another sort and back restores it (spec story 9). The desktop asks for the page in Custom only after the core has answered.
- *A move through the CLI or MCP* (Q37). It moves within the Custom Order the AI read (`--sort custom`, sort `custom`) and switches the List to Custom, so the person sees the AI's order: the desktop follows the remembered sort when it notices an outside change, unless a Task on screen holds unsaved text.

A move that would change nothing is refused and changes nothing, not even the sort. Changing a priority never goes through this write, so it only re-sorts. A page listing and the rewrite read one definition of each sort's order (`search::ranked` and `search::order_by`), so the order a List starts from is exactly the order it listed.

**Remembered sorts.** Each view (All tasks, Inbox, each List) remembers its sort in the core (`view_sorts`), so it survives restarts. The desktop reads them before it asks for its first page, so a view never opens by Priority and then reshuffles (the list never moves by itself). Only the desktop chooses a sort; a move from any interface switches its List to Custom. Neither a sort change nor the rewrite that starts a Custom Order is audited or changes a revision: they are how the person looks at their Tasks, a viewing preference. The move itself is audited. All tasks cannot be Custom, since positions mean nothing across Lists.

**Surprising choices.**
- The CLI and MCP offer after and first only, like the sidebar. The desktop also places a Task *before* a row, because its pages replace one another: on a later page the Task before the top row is not loaded.
- Dragging is off whenever any search or filter is active (status, priority, difficulty, tag, search), not only search and tag filters, and in views spanning several Lists: a filtered page hides part of a group, and the person should see the whole group they arrange. A drag or Alt+Up/Down there shows a brief notice instead, "Turn off filters to reorder Tasks" or "Open one List to reorder Tasks" (Q36): about 2 seconds, in its own polite live region above the new Task toast, never focused, and nothing moves.
- Choosing Custom again brings back a List's own Custom Order rather than starting over from the screen: Q35 asked for the screen order when a List shows Custom for the first time, and spec story 9 promises the order back after looking by another sort. A drag under another sort always starts from the screen, since that is the order the person dropped into.
- Exports carry each Task's `position`; the format version stays.

**Known limits.** A move happens within the page on screen; a Task cannot be dragged to another page of the same List in one step. Switching to Custom from a later page shows the first page again, since the earlier sort's cursor means nothing in the new order. A move rewrites the positions of the Tasks it passes, and starting a Custom Order rewrites every Task of the List, in one transaction. Measured on a synthetic List of 5,000 Tasks (`switching_a_list_of_5000_tasks_to_custom_is_quick`): 30 ms by choosing Custom and 40 ms by a drag in a debug build, 16 and 20 ms in a release build, so it needs no index or batching of its own.

# Lists nest like Note Folders, only to group

Status: accepted (2026-11-09)

Lists were flat. The owner wanted to group Lists the way Note Folders group Notes, so a List may now sit inside another, up to the same five levels as Note Folders, with one rule for both trees. A List shows only its own Tasks: nesting groups Lists and never rolls Tasks up, because a roll-up would make a parent's Custom Order, counts and removal ambiguous. Inbox stays at the top level and holds no Lists, since it is where unsorted capture lands. Removing a List that holds Lists follows the existing container rule (ADR 0002): what is inside is hidden, not changed, and comes back with it.

**Implementation (Ticket 12, schema v21).** `lists` gains a nullable `parent_id` naming another List, exactly as `note_folders` keeps its tree, so both trees share one module, `tree`: the depth limit (`MAX_DEPTH`, 5), the cycle check and the ancestor and subtree walks, parameterised by table and returning each kind's own refusal (`ListCycle`/`ListTooDeep`, `NoteFolderCycle`/`NoteFolderTooDeep`). Manual order (ADR-0007) now keys siblings by tree and parent for both, so the Lists are no longer one flat group but one group per parent; `reorder_list` is the one placement entry, keeping a List under its parent unless the caller names another (`ListParent`, as `FolderParent`), `place_list` names one for a sidebar drop, and `move_list` puts it at the bottom of another parent, recorded as `list.move`. Whether a placement is a move or a reorder is decided from the List as the write reads it. The Removed rule uses one recursive "hidden containers" query for both tables: a Task is hidden when its List or any List around it is in Removed. List names are unique, ignoring case, only among siblings not in Removed (owner decision Q33, below). `list_lists` reads the tree parents first, siblings in manual order, so one keyset page order serves the sidebar, the CLI and MCP; exports carry `parent_id`, and a Markdown export writes a Sub-List's Tasks to `Tasks/<List>/<Sub-List>.md`.

**Amended 2026-11-10 (owner decisions Q33, Q34).** List names follow the Note Folder rule: unique, ignoring case, among the Lists that share a parent, the top-level Lists being siblings of each other, so "Adamaja IT › Reports" and "Personal › Reports" may coexist. Schema v21 replaces the global unique index with one per parent (`lists_sibling_name`); names that were unique among all Lists stay valid, so no row changes. Create, rename, restore, move and drop all refuse a sibling's name with `name_conflict` ("A List with this name already exists here"). Every interface names a List by id (desktop, CLI `--list ID`, MCP `list_id`); where a person picks a List by its name, the window shows its path. Lists start collapsed in the sidebar, like Note Folders, and the window remembers the open ones the same way (the ids of the open rows, per window).

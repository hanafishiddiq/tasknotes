# Lists nest like Note Folders, only to group

Status: accepted (2026-11-09)

Lists were flat. The owner wanted to group Lists the way Note Folders group Notes, so a List may now sit inside another, up to the same five levels as Note Folders, with one rule for both trees. A List shows only its own Tasks: nesting groups Lists and never rolls Tasks up, because a roll-up would make a parent's Custom Order, counts and removal ambiguous. Inbox stays at the top level and holds no Lists, since it is where unsorted capture lands. Removing a List that holds Lists follows the existing container rule (ADR 0002): what is inside is hidden, not changed, and comes back with it.

**Implementation (Ticket 12, schema v21).** `lists` gains a nullable `parent_id` naming another List, exactly as `note_folders` keeps its tree, so both trees share one module, `tree`: the depth limit (`MAX_DEPTH`, 5), the cycle check and the ancestor and subtree walks, parameterised by table and returning each kind's own refusal (`ListCycle`/`ListTooDeep`, `NoteFolderCycle`/`NoteFolderTooDeep`). Manual order (ADR-0007) now keys siblings by tree and parent for both, so the Lists are no longer one flat group but one group per parent; `reorder_list` keeps a List under its parent, `place_list` changes parent and place in one write, and `move_list` puts it at the bottom of another parent, recorded as `list.move`. The Removed rule uses one recursive "hidden containers" query for both tables: a Task is hidden when its List or any List around it is in Removed. List names keep the rule they had: unique, ignoring case, among all Lists not in Removed, wherever they sit, so a move never meets a name conflict. `list_lists` reads the tree parents first, siblings in manual order, so one keyset page order serves the sidebar, the CLI and MCP; exports carry `parent_id`, and a Markdown export writes a Sub-List's Tasks to `Tasks/<List>/<Sub-List>.md`.

# Ticket 13 — Backup, validated restore, and export: plan (2026-10-26)

Started on the owner's instruction (Tickets 05–18 autonomy: Draft PR per ticket, AI review gate, no merge, synthetic data only, never the owner's real data directory). Built on `integration/tasknotes-v1-07-18` at a05b6ec (Tickets 07–11, 14–16; schema v12). Ticket 12 (MCP) is built in parallel and takes schema v14; this ticket uses v13.

## Scope

Automatic local backups with the 7 daily / 4 weekly / 3 monthly policy, a validated restore that no stale writer (window, CLI, MCP) can undo, and JSON/Markdown export that respects Exclude from AI. Surfaces: core operations, `tasknotes backup …` / `tasknotes export …`, and a small "Backups and export" section in desktop Settings.

## Test seams (pre-agreed in the spec, Q48)

2. **Adapter contract**: the built `tasknotes` binary as a separate process, plus the library `run` for the terminal-confirmed restore (a test cannot own a TTY): `crates/tasknotes-cli/tests/backup.rs`.
3. **Desktop**: the Settings section and the invoke wrapper behind the mocked Tauri seam: `src/data-settings.test.tsx`. Native GUI acceptance stays open (owner check).

## Decisions made by the implementer (owner may revisit)

- **Snapshot = `VACUUM INTO`.** Saya pilih ini karena ia mengambil snapshot konsisten di dalam satu read transaction WAL (writer lain tetap jalan, tulisan yang belum commit tidak ikut), hasilnya file ringkas, dan tidak butuh koneksi tujuan. Written to a hidden `.<id>.partial` (pre-created 0600), synced, then renamed; a manifest `<id>.json` (written tmp+rename) records `manifest_version`, `id`, `kind`, `created_at`, `schema_version`, `size_bytes`, `sha256`. A snapshot without a valid manifest is never listed. No user text in a manifest, so listing backups is safe for AI interfaces.
- **Location: `backups/` next to `tasknotes.db`** in the data directory (dir 0700, files 0600), outside any Git checkout.
- **When: at most one automatic backup per day (local day since the review fixes), while any process runs.** Desktop: at launch, then an hourly check on a background thread. CLI: every data command calls `ensure_daily_backup` after the trust check, best effort and silent (stderr stays empty per the CLI contract; the next process tries again). Two processes racing may both take one; retention keeps the newest of the day, so no lock file is needed. MCP (Ticket 12) should call `ensure_daily_backup` at start-up and periodically, like the desktop.
- **Retention: pure `backup::retained`, restic-style.** Each rule keeps the newest backup of each of its N most recent periods *that have a backup* (days; Monday–Sunday weeks; calendar months; all UTC), and a backup kept by any rule stays. Superseded by review fixes 4–6: Daily backups alone follow it, Manual backups keep the newest 10, Pre-restore backups are never pruned, days are local. Saya pilih "periode yang punya backup" agar Tasknotes yang lama tidak dibuka tidak menghapus semua backup lama sekaligus. (The original UTC choice was replaced by local days in review fix 6.)
- **Restore validation, before anything live changes:** the id must be one this module made (no paths); size and SHA-256 must match the manifest; then on a private staging copy: SQLite must open it, `user_version` in 1..=13 (newer → `unsupported_schema`), `PRAGMA integrity_check` must be `ok`, `PRAGMA foreign_key_check` empty, and the forward migrations must succeed. Any failure is `invalid_backup` (exit 5) and the live file is untouched.
- **Restore swap: SQLite online backup API, one `step(-1)`,** from the staging copy into the live database. It holds SQLite's write lock on the live file for the whole copy, so other connections see the old data or the new, never a mix, and the file stays in WAL mode. A writer holding the lock is waited for up to the 5 s busy timeout, then the restore is refused (`storage_unavailable`, message "Try again"). Saya pilih ini, bukan rename file, karena proses lain bisa sedang membuka file lama (inode lama, -wal/-shm tidak cocok).
- **Writer coordination: Restore Epoch (schema v13, table `database_epoch`).** A random token in the database. Restore writes a fresh token into the staging copy before the swap, so the token changes atomically with the data. Every store remembers the token it opened with; `connect()` checks it on every operation and `begin_write()` checks it again *after* taking the write lock (`BEGIN IMMEDIATE`), so a restore cannot slip between check and write. A stale store gets `database_restored` (exit 4, like a revision conflict: reload and retry). Every write transaction in the core now goes through `begin_write`; a source-scan test fails if one is opened any other way. The restoring store carries on with the new token (shared by its clones).
- **Desktop after a restore made elsewhere:** one `invoke` wrapper (`src/lib/invoke.ts`) for all core calls; on `database_restored` it calls `adopt_restored_data` and reloads the window, so nothing cached is written back. A restore made in the window reloads it too.
- **Pre-restore backup** of the live data is taken after validation and before the swap; restoring it undoes the restore.
- **Who may restore:** the desktop, and the CLI only after the person types `restore` at an interactive terminal (same deliberate-step model as `access grant`; not a security barrier, Q47). MCP is refused in the core (`desktop_only`). The command is `tasknotes backup restore <id>` to keep the CLI's `<noun> <verb>` grammar.
- **Export (core `export_data`):** one read transaction; everything including Removed items (labeled, so they stay recoverable — export deletes nothing). JSON: one document (`format: "tasknotes-export"`, `format_version: 1`, lists, tasks with tags and progress history, note_folders with `parent_id`, notes, note_links). Markdown: `README.md`, `Tasks/<List>.md` (+ `Inbox.md`), `Notes/<folder tree>/<Note title>.md` with a JSON-quoted front-matter header; names sanitized and de-duplicated case-insensitively; Removed folders/Lists/Tasks get "(Removed)". Never overwrites: written under a hidden partial name, renamed into place.
- **Privacy in export:** the note filter goes through `privacy::shared_with_ai_sql` / `note_shown_sql`. An AI-facing store can never ask for private Notes (`desktop_only`), so its export is exactly what it may read; links to private Notes are left out with them. The desktop leaves them out by default; the person ticks "Include Notes marked Exclude from AI". The CLI has no such option (it is AI-facing, Ticket 10).
- **Desktop export destination:** the Downloads folder under `Tasknotes export YYYY-MM-DD HH.MM(.json)`, with ` (2)` etc. when taken. Saya pilih ini karena belum ada dialog plugin dan desain melarang dialog; Settings shows the saved path.

## Review fixes (2026-10-26)

`/code-review` found ten issues; each became a test first (the reviewer's reproductions, ported into `tests/backup_restore.rs`, `tests/export.rs` and CLI `tests/backup.rs`), then a fix. Decisions marked **coordinator decision** were made by the review coordinator, not the owner, and the owner may revisit them.

1. **Data loss in restore (fixed).** Writes landing between the Pre-restore snapshot and the swap were in neither copy (402 of 872 in the reviewer's run). Restore now fences writers first: after validation, under `begin_write` (BEGIN IMMEDIATE + epoch check), it replaces the live Restore Epoch with a fence token `restoring-…` that no store holds, so every other writer in every process (and this store's clones) is refused from that commit on; then the Pre-restore snapshot; then the swap with the final epoch. While the fence is up the restore holds an OS file lock on `backups/.restore.lock`; `TaskStore::open` and `adopt_restored_data` meanwhile get `RestoreInProgress` (`storage_unavailable`, "try again"); a fence whose lock is free (the restoring process stopped; the live data was not replaced, the swap is last) is lifted with a fresh epoch on the next open. A restore that fails after fencing puts the old epoch back. Saya pilih file lock (bukan timeout) agar restore yang mati tidak membuat database terkunci selamanya. Test: `no_write_that_succeeds_during_a_restore_is_lost` (15 rounds), `a_store_cannot_open_mid_restore_and_a_stopped_restores_fence_is_lifted`. Not covered by a test: the "restore fails after the fence" path (no seam to fail the Pre-restore snapshot or the swap mid-way).
2. **Foreign file with a forged `user_version` (fixed).** After migrating the staging copy, its schema (every table, index, trigger and view, and each table's columns) must equal that of a database freshly created in memory by the same `migrate`. Test: `a_foreign_database_with_a_plausible_schema_version_is_refused` (v12 and v13), `a_backup_from_an_older_schema_is_upgraded_on_restore`.
3. **Audit stays append-only across restore (coordinator decision).** Every live Audit Entry the snapshot lacks is appended to the restored data in append order with its id; its `hidden_from_ai` is frozen to whether AI could see it at restore time (the Note that hid it may be missing or shared in the restored data). A `backup.restore` entry (entity = Backup id, interface, no user text) is recorded. Refusal entries now go through `begin_write`, so one racing a restore is either committed before the fence (and carried over) or refused and reported as `AuditUnrecorded`. Progress Entries are user state and return to the snapshot. Tests: `a_restore_keeps_the_audit_history_and_records_itself`, `a_refusal_racing_a_restore_is_kept_or_reported_unrecorded`.
4. **Pre-restore backups are never auto-pruned (coordinator decision).** `PRE_RESTORE_KEPT` is gone. Each restore adds one full copy of the data to `backups/`, so the folder grows with every restore; the person can delete old Pre-restore backups from the folder by hand. Test: `pre_restore_backups_are_never_pruned`.
5. **Retention buckets (coordinator decision).** Each kind is its own bucket: Daily backups follow 7/4/3; the `MANUAL_KEPT` = 10 newest Manual backups are kept; a Manual backup prunes only Manual backups and no longer counts as the day's Daily one. Tests: `manual_backups_are_their_own_bucket_of_ten` (fake clock), the existing 148-day policy test.
6. **Local days (coordinator decision).** Days, weeks and months for the daily check and retention are local calendar days (`calendar::TimeZone::Local`, offset from `localtime_r`, so daylight saving follows the system). Backup ids stay UTC so they sort by time. Tests inject `TimeZone::Fixed`: `backup_days_follow_the_local_calendar`, `calendar::tests::a_fixed_offset_moves_the_day_boundary`. Saya pilih `libc::localtime_r` (sudah ada di dependency tree) daripada menambah `chrono`.
7. **Export.** Every file is created fresh (`create_new`, 0600; directories 0700), synced, and moved into place without replacing anything: a JSON file by hard link (fails if the name is taken) then removing the partial name, falling back to a checked rename on a file system without hard links; a Markdown directory by `rename`, which refuses a file or non-empty directory (an empty directory created there in between is replaced, losing nothing). Markdown names are compared after NFD → case fold → NFC (`text_fold::fold`), so NFC and NFD "Café" get two files. A destination without a name is `InvalidExportDestination`. Tests: `notes_whose_titles_differ_only_in_unicode_form_get_two_files`, `exports_are_private_to_the_persons_account`, `a_destination_without_a_name_is_its_own_error`.
8. **Robustness.** The CLI reports a failed automatic backup as `"warnings":[{"code":"backup_failed",…}]` in the envelope (success or failure; stderr stays empty), and `backup_retention_failed` when a backup was taken but retention failed: `create_backup` / `ensure_daily_backup` now return `NewBackup { backup, retention_error }`, so a successful backup is never reported as failed. The desktop logs both. Snapshot and manifest are both written under partial names and synced; the snapshot is renamed first and the manifest last, and orphan snapshots without a manifest (and manifest partials) older than an hour are cleaned. `sync_dir` errors are returned, except `InvalidInput` (a file system that cannot sync a directory). Tests: CLI `a_failed_automatic_backup_is_reported_in_the_envelope`, `an_interrupted_backup_or_restore_leaves_nothing_that_looks_like_a_backup` (fails with orphan cleanup removed).
9. **Epoch guard widened.** A store's `connect()` connection is `query_only`; `begin_write` lifts it only after taking the write lock and checking the epoch. So a deferred `transaction()` or an autocommit write that skips `begin_write` fails in every test that reaches it (unit test `a_store_connection_writes_only_through_begin_write`); the whole suite passes with this on. The source scan also allows raw connections only in `tasks.rs` and `backup.rs`. Not guaranteed: once a `begin_write` transaction ends its connection stays writable (each operation drops its connection).
10. **Smells.** `calendar` module (shared `civil_from_days`, `DAY_MS`, `TimeZone`); one `open_connection` (busy timeout) and one `migrate` used by open, restore staging and the reference schema; `manifest_name`; `Interface::may_restore` (exhaustive match) instead of `== Interface::Mcp`.

**For Ticket 12 (MCP):** `ensure_daily_backup()` stays callable from any adapter (it now returns `Option<NewBackup>`); the MCP server must call it at start-up and periodically (e.g. hourly, like the desktop) and report `retention_error` or an `Err` without failing its tools. Restore stays refused for MCP (`Interface::may_restore`).
